# 1. IDTA AAS Specifications: 표준 문서 묶음을 읽는 법

## 학습 목표

- AAS가 해결하려는 상호운용성 문제를 설명한다.
- 메타모델·API·서브모델 템플릿·교환 패키지를 구분한다.
- 문서 버전과 소프트웨어 버전을 혼동하지 않는다.

## 1. AAS란 무엇인가?

Asset Administration Shell은 보통 **자산 관리 셸**이라고 부릅니다.

“셸”은 자산의 정보를 표준 방식으로 제공하는 디지털 표현이라고 이해하십시오. 실제 모터 자체도, 모터를 제어하는 PLC 프로그램 자체도 아닙니다.

```text
실제 모터
   │ 디지털로 표현
   ▼
AAS
   ├─ 어떤 자산인가?
   ├─ 어떤 정보를 제공하는가?
   └─ 관련 서브모델은 어디에 있는가?
           ├─ 식별 정보
           ├─ 기술 특성
           └─ 문서 정보
```

제조사마다 `rated_current`, `NominalCurrent`, `정격전류`라고 표기하면 프로그램이 매번 별도 해석해야 합니다. AAS의 구조, 합의된 서브모델 템플릿, 속성 의미 식별자를 함께 사용하면 재사용 가능한 교환이 가능해집니다.

**단, AAS 구조만 동일하다고 의미까지 동일해지는 것은 아닙니다.** 같은 개념을 식별하는 semanticId와 단위·자료형·템플릿의 합의가 중요합니다.

## 2. IDTA는 무엇인가?

Industrial Digital Twin Association은 AAS 관련 사양과 서브모델 템플릿 등을 제공하는 단체입니다. 공식 [AAS Specifications](https://industrialdigitaltwin.org/en/content-hub/aasspecifications)는 관련 문서의 진입점입니다.

사이트는 “모든 내용을 순서대로 읽는 책”이 아니라 **필요한 규칙을 찾아가는 문서 지도**로 활용하십시오.

## 3. Part별 역할

이 표는 본 학습의 기준인 v3.1 메타모델 문서가 설명하는 사양 분리 구조를 중심으로 정리했습니다. 상세 판본은 공식 사이트에서 확인하십시오.

| 영역 | 배우는 내용 | 해당하지 않는 내용 |
|---|---|---|
| Part 1: Metamodel | AAS·Submodel·Property·Reference의 구조와 제약 | 서버의 모든 배포 방법 |
| Part 2: API | 조회·생성·갱신 등 서비스의 계약 | 장치 사양이 사실인지의 증명 |
| Part 3 계열: Data Specifications | 개념 설명 등에 쓰는 데이터 사양 템플릿 | 모든 산업 서브모델의 항목 목록 |
| Part 4: Security Metamodel | 보안 관련 모델 | 이것만으로 완성되는 운영 보안 |
| Part 5: AASX Package | AAS 관련 데이터·파일의 패키지 교환 | 실시간 메시지 버스 |
| Submodel Templates | 식별·기술 특성 등 특정 업무의 의미와 항목 | 공통 메타모델 자체 |

**특히 구분할 것:** Data Specification Template은 개념 설명 같은 정보 구조를 정의하며, Submodel Template은 특정 업무에서 어떤 서브모델 항목을 제공할지 정의합니다.

JSON/XML/RDF 교환 형식의 매핑·스키마는 해당 사양의 공식 저장소와 판본을 확인합니다. “Part 1에 RDF라는 단어가 있으니 내 PLC 온톨로지가 이미 표준화됐다”는 뜻은 아닙니다.

## 4. 메타모델과 템플릿의 차이

메타모델은 다음을 허용합니다.

> Submodel 안에 Property를 넣고, Property에 valueType과 value를 표현한다.

특정 서브모델 템플릿은 다음을 더 구체화할 수 있습니다.

> 이 업무에서는 특정 의미의 속성을 제공하고, 그 자료형·카디널리티·의미 ID를 이 방식으로 사용한다.

“Property를 쓸 수 있다”와 “어떤 Property를 반드시 써야 한다”는 다른 수준의 규칙입니다.

가상의 `TechnicalData`라는 idShort를 붙이는 것만으로 공식 Technical Data 템플릿을 준수한 것은 아닙니다. 공식 semanticId·항목·타입·구조·버전을 대조해야 합니다.

## 5. 규범 문서의 표현 읽기

| 표현 | 읽는 방법 |
|---|---|
| MUST / SHALL | 반드시 따라야 하는 요구 |
| MUST NOT / SHALL NOT | 금지 |
| SHOULD | 특별한 이유가 없으면 따를 권고 |
| MAY | 선택 가능한 동작 |
| Note / Example | 설명 또는 예; 그 자체를 필수 규칙으로 오해하지 않음 |

클래스 표의 `0..1`은 없어도 되지만 있으면 하나, `1`은 필수 하나, `0..*`는 여러 개 가능이라는 의미입니다.

선택 필드라도 해당 업무 템플릿이나 조직 등록 정책에서는 필수가 될 수 있습니다. 반대로 내부 요구를 표준 자체의 필수 요구라고 표현하면 안 됩니다.

## 6. 네 종류의 버전을 따로 기록하기

| 버전 | 예시 표현 | 질문 |
|---|---|---|
| AAS 메타모델 | v3.1 | 어떤 구조와 제약을 사용하나? |
| API 사양 | 채택한 Part 2 판본 | 어떤 서비스 계약을 사용하나? |
| 서브모델 템플릿 | 해당 템플릿의 판본 | 어떤 업무 의미 구조를 사용하나? |
| 구현 소프트웨어 | BaSyx 이미지·SDK의 고정 버전 | 무엇이 실제 실행되나? |

여기에 실제 자산 데이터 revision도 따로 있습니다. 모든 숫자가 같아야 한다고 가정하지 않습니다.

“BaSyx V2”의 V2는 곧 “AAS 메타모델 v2”라는 뜻이 아닙니다.

## 7. 읽기 실습: 모터 등록에 필요한 규칙 찾기

### 과제

다음 요구를 어느 문서에서 확인해야 하는지 분류하십시오.

1. AAS에서 자산 식별 정보를 표현하는 방법.
2. AAS를 HTTP로 조회하는 방법.
3. 명판 정보를 어떤 항목·의미 ID로 표현하는지.
4. PDF를 포함한 교환 파일을 만드는 방법.
5. 정격 전류 12.5 A가 실제 장치 사양과 맞는지.

### 해답

1. Part 1의 AAS·AssetInformation.
2. Part 2와 선택한 서버의 API 지원 문서.
3. 적합한 Submodel Template과 그 의미 정의.
4. Part 5와 구현 도구의 패키지 지원.
5. 표준 구조만으로 해결되지 않음. 제조사 문서·명판·승인 근거 필요.

## 자주 하는 오해

- **AAS는 데이터베이스 제품이다:** 아닙니다. 모델·교환·서비스 관련 표준 체계이고, 저장소는 구현입니다.
- **AAS를 쓰면 자동 디지털 트윈이 완성된다:** 아닙니다. 수집·동기화·출처·모델·서비스가 추가로 필요합니다.
- **모든 실측 데이터를 AAS Property에 계속 넣으면 된다:** 가능 여부와 별개로 고빈도 이력 저장의 적합성을 검토해야 합니다. 이 설계는 시계열 저장소와 연결합니다.
- **공식 템플릿 대신 이름만 맞추면 된다:** 소비자가 의미를 안정적으로 해석할 수 없습니다.
